# React 工程规范索引

本规范面向 React 产品工程，和具体业务、后端协议、UI 组件库及 `@richie696/*` 底座无关。目标是让开发者仅看目录和文件名，就能判断代码负责什么、依赖谁、在哪里扩展。React 视图遵循函数组件和 Hooks；可独立存在的协议、状态或生命周期服务可以使用对象封装，不建立页面继承树。

| 文档 | 回答的问题 | 使用时机 |
| --- | --- | --- |
| [UI/UE 设计规范](REACT_UI_UX_STANDARD.md) | 页面如何组织信息、交互、状态、可访问性、响应式、国际化和视觉皮肤？ | 设计或改动页面之前 |
| [编码规范](REACT_CODING_STANDARD.md) | 组件、Hooks、服务、状态、请求与测试各由谁负责？ | 写代码与 Review 时 |
| [项目骨架规范](REACT_PROJECT_SKELETON.md) | 工程、目录、文件、SCSS 层和依赖方向如何安排？ | 创建工程、增加 feature 或拆分大文件时 |

上述三份是通用规则。使用本仓库底座时，另读 [Richie React 底座 API 使用指南](RICHIE_FOUNDATION_USAGE.md)；它只解释已发布 API 的真实能力和推荐位置，不改变通用工程规范。某个产品的页面地图、领域规则、色值、接口路径和迁移清单应保留在该产品仓库。

## 共同原则

1. 一个模块、文件或对象只承担一个主要变化原因；相同业务规则保持唯一事实来源。不要凭行数机械拆分，也不要把路由、协议、规则、状态和 JSX 放进同一个文件。
2. `app` 负责装配，`core` 负责全局基础设施，`shared` 负责真实跨 feature 复用，`features` 负责业务能力。下层不能导入上层，feature 不能深层导入别的 feature 私有文件。
3. 产品皮肤由产品拥有。SCSS 组织样式，CSS 自定义属性承载运行时语义 token；组件样式只消费 token。框架底座与具体 UI 组件库、品牌色保持分离。
4. 状态放在最小合适作用域：组件交互本地化，可分享状态放 URL，服务端状态由数据层持有，跨 feature 状态有明确所有者。订阅、请求、轮询和观察器必须按所有者生命周期清理。
5. 文档区分目标规范与现状。建立规范不会自动完成旧工程的重构、主题迁移或端到端验收；迁移需要逐 feature 保持行为并验证。

规范面向新的 React 工程，也可作为已有工程的增量迁移目标。目录仅在职责实际存在时创建；不要为凑齐骨架预建空文件、空接口或无用途的抽象。
